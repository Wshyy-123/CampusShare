## 一、测试目标

1. 验证体育预约**使用前取消**后，占用被解除、记录被保留、重复提交不产生副作用（XIA-7 三条验收标准）。
2. 验证体育预约**扫码签到 / 签退**能够记录时间并查询，且超时被取消的预约不能被迟到扫码恢复（XIA-8 三条验收标准）。
3. 验证取消、签到、签退与后台超时处理在状态、时间和并发上互不矛盾。
4. 验证接口契约：响应结构、错误码、时间格式、权限边界与文档一致。

## 五、测试策略

### 5.1 分层

| 层次 | 目的 | 主要用例 |
|---|---|---|
| 接口契约测试 | 字段、状态码、错误码是否与文档一致 | 接口测试类用例 |
| 页面功能测试 | 用户能否完成取消 / 签到 / 签退并看到正确反馈 | 功能测试类用例 |
| 后台任务测试 | 超时取消、记违规、重复扫描是否幂等 | XXC-215~218 |
| 权限与安全 | 他人预约、未登录、非法参数是否被正确拒绝 | 安全相关类用例 |
| 一致性检查 | 状态条件更新、锁内重读是否避免"既签到又取消" | XXC-217、XXC-205 |

### 5.2 用例设计方法

- **状态迁移**：以 `RESERVED / CHECKED_IN / COMPLETED / CANCELLED` 为状态，逐一验证三种操作的受理与拒绝。
- **边界值**：取开始前 1 秒、开始时刻、开始后 14 分 59 秒、15 分整。
- **等价类**：体育资源与非体育资源、本人与他人、登录与未登录、存在与不存在。
- **幂等**：重复取消、重复签到、重复签退、后台重复扫描。
- **异常**：非法预约号、状态冲突、已超时取消。

### 5.3 状态迁移矩阵

| 当前状态 | 取消 | 签到 | 签退 |
|---|---|---|---|
| RESERVED（开始前） | 允许 → CANCELLED / USER_CANCEL | 拒绝（未到时间） | 拒绝（未签到） |
| RESERVED（开始后 15 分钟内） | 拒绝（已到开始时间） | 允许 → CHECKED_IN | 拒绝（未签到） |
| RESERVED（超过 15 分钟） | 拒绝 | 拒绝（已超时） | 拒绝（未签到） |
| CHECKED_IN | 拒绝（已签到） | 幂等返回 200 | 允许 → COMPLETED |
| COMPLETED | 拒绝（已完成） | 拒绝（已完成） | 幂等返回 200 |
| CANCELLED / USER_CANCEL | 幂等返回 200 | 拒绝（已取消） | 拒绝（已取消） |
| CANCELLED / NO_SHOW | 拒绝（超时取消） | 拒绝（已取消，不恢复） | 拒绝（已取消） |

### 5.4 时间口径

| 判定 | 口径 | 可配置项 |
|---|---|---|
| 取消 | `当前时间 < start_at` | 无 |
| 签到开始 | `当前时间 >= start_at - 提前分钟` | `app.sports.check-in-early-minutes`，默认 0 |
| 签到截止 | `当前时间 < start_at + 15 分钟`，15 分整即拒绝 | `app.sports.check-in-grace-minutes`，默认 15 |
| 后台超时 | 与签到截止同一口径，扫描间隔 10 秒 | `app.sports.no-show-cron` |
| 签退 | 状态为 CHECKED_IN 即可，不设时间上限 | 无 |

## 七、执行安排

| 阶段 | 内容 | 建议时间 |
|---|---|---|
| 准入检查 | 后端可启动、数据库脚本已应用、演示数据就绪、接口契约冻结 | 开始前 |
| 冒烟 | 只跑 13 条 P0，确认主流程可用 | 第 1 天 |

**准入条件**：分支已合入测试环境可部署的版本；数据库为 `001`~`004`；演示数据未被其他测试破坏。

**准出条件**：

1. 13 条 P0 全部通过；P1 无未解决缺陷。
2. XIA-7、XIA-8 的 6 条验收标准都有对应用例的实际执行记录。
3. 已知限制（漏签退、提前签到口径等）有明确结论，不以"未执行"代替通过。
4. 缺陷单已关联对应工作项，且重跑通过。

**记录方式**：在 PingCode 测试计划中执行并填写结果；失败用例记录实际值、请求号 `requestId` 和截图。

## 八、风险与依赖

| 风险 / 依赖 | 影响 | 应对 |
|---|---|---|
| 登录（XIA-1）未实现，身份用调试请求头 | 权限用例只验证了服务端归属判断，未验证真实会话 | XIA-1 合并后必须重跑 XXC-108、XXC-109、XXC-207 |
| 创建预约（XIA-5）未合并 | XXC-112 无法端到端验证"释放后可再预约" | 暂用 SQL 校验时段无有效占用，接口就绪后补跑 |
| 后台任务每 10 秒扫描 | 超时类用例需要等待，手工执行节奏不稳 | 用 SQL 构造 `start_at`，执行时预留 15 秒等待 |
| 本机 8080 被 `ApplicationWebServer` 占用 | 前端代理默认指向 8080 会失败 | 后端用 8081，前端设 `VITE_PROXY_TARGET` |
| 时间边界依赖系统时间 | 手工在"开始前 1 秒"操作容易误差 | 边界用例优先用自动化测试或直接改库构造数据 |
| 用例库模块与成员未知 | 导入后可能全部进入"无模块用例" | 见第九节，先建模块或导入后批量移动 |

## 九、导入 PingCode 说明

1. 打开测试库 `XXC` → 用例 → 导入 → 选择 `PingCode-测试用例-XIA-7-XIA-8.xlsx`。
2. 文件保留了模板的第 1 行说明与第 2 行表头，数据从第 3 行开始，共 30 行。
3. **模块列为空**：模板要求填写用例库中已存在的模块名，本文件留空，导入后会归入"无模块用例"。如需按模块组织，请先在用例库建好模块（建议 `体育场地/取消履约`、`体育场地/扫码签到签退`），再让我按模块重出一版。
4. **编号**：`XXC-101`~`XXC-112`（XIA-7）与 `XXC-201`~`XXC-218`（XIA-8），前缀取自测试库地址中的 `XXC`；若测试库标识不是 `XXC`，导入前统一替换前缀即可。
5. 维护人、关注人留空，导入后在 PingCode 内批量指派。
6. 同一编号重复导入会覆盖原用例，适合修订后重新导入。
