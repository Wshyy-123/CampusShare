# 校享 CampusShare 开发环境与协作约定

项目：校享 CampusShare——校园公共场地预约与管理平台。

## 一、统一开发环境

| 类别 | 统一方案 |
|---|---|
| 前端框架 | Vue 3 + Vite |
| 前端语言 | TypeScript |
| 前端开发工具 | VS Code |
| 前端运行环境 | Node.js 24 |
| 前端包管理器 | npm |
| 后端语言 | Java 21 |
| 后端框架 | Spring Boot，选用与Java 21兼容的正式版本 |
| 后端开发工具 | IntelliJ IDEA |
| 数据库 | MySQL 8.4 LTS |
| 版本控制与代码托管 | Git + GitHub |
| 持续集成 | GitHub Actions |
| 项目管理 | PingCode |

Spring Boot及各项依赖的具体版本在项目初始化时固定。Node、npm、JDK和MySQL的补丁版本写入启动说明；前端提交锁文件。IDE不要求所有成员使用相同补丁版本。

构建工具建议采用Maven 3.9.x，并在项目中提供Maven Wrapper，由后端成员确认后固定。

## 二、项目与团队协作

### 产品与演示形式

- 浏览器访问，兼顾电脑和手机。
- 体育签到、签退使用手机真实扫码。
- 图书馆刷卡通过模拟入口产生到馆确认事件。

### 数据库协作

- 开发阶段每人使用自己的本地数据库。
- 后续设置一套共同联调环境。
- 表结构、初始化数据和变更脚本统一提交到仓库，按版本同步。
- 数据库连接信息通过本地配置或环境变量填写，仓库提供不含真实密码的配置示例。

### Git协作

- 仓库地址：[Wshyy-123/CampusShare](https://github.com/Wshyy-123/CampusShare)。
- 仓库公开性：Public；默认分支：`main`。
- 一个GitHub仓库，设置`frontend/`、`backend/`、`docs/`目录。
- 每项功能建立独立分支。
- 提交和合并请求关联PingCode工作项编号，例如`XIA-5`。
- 合并前由另一名开发人员检查，具体检查人员由开发团队安排。
- 使用GitHub Actions运行约定的自动检查和构建。

## 三、代码风格与API规范草案

本节供开发人员共同评审，评审后将具体配置和接口契约提交到仓库。

### 代码风格草案


- 文件编码统一UTF-8，换行统一LF；项目提交格式化配置，由工具处理格式。
- 前端默认2空格缩进，Java默认4空格缩进；最终以团队选定的格式化器配置为准。
- Vue组件文件与Java类使用PascalCase；变量、方法及JSON字段使用camelCase；数据库表和列使用snake_case。
- 前端统一Vue 3单文件组件和TypeScript，采用`<script setup lang="ts">`；接口请求与类型集中维护，不在每个页面重复定义。
- 后端区分接口入口、业务逻辑和数据访问职责，预约规则与超时任务共用必要的业务逻辑；不把是否冲突或是否可取消只交给前端判断。
- 接口入参与出参单独定义，不直接将数据库实体当成对外接口契约；格式化器、静态检查工具及其版本由开发人员评审后锁定。
- 前端类型检查单独纳入检查命令，不能只以Vite页面能启动判断类型正确；避免为绕过检查普遍使用`any`或关闭类型检查。
- Agent生成代码与手写代码遵守相同的检查要求；提交者应能解释修改及验证结果。

### API约定草案

- 前后端维护同一份接口契约，先覆盖拟进入Sprint 1的故事；地址、方法、字段、类型、必填项、权限、成功与失败示例都写清。
- 路径统一以前缀`/api/v1`开始，JSON字段使用camelCase。查询使用GET；预约、取消、签到、签退等状态改变通过明确的写入请求完成。
- 建议响应使用`code`、`message`、`data`，并让HTTP状态表达成功、未登录、无权限、资源不存在或状态冲突；具体错误码表由前后端共同确认。
- 查询分页建议统一`page`、`size`，约定页码从1开始；响应统一`items`、`total`、`page`、`size`。字段名称属于草案，不是已实现接口。
- 业务时区统一按Asia/Shanghai解释；对外时间建议使用带偏移的ISO 8601格式，例如`2026-10-20T10:00:00+08:00`。超时与有效时间以服务端时间为准。
- 状态值及转换条件建立同一份字典；座位、体育、讨论室、教室各自规则按已确认PB执行，不能为了统一接口把不同规则合并。
- 登录身份由服务端识别。创建预约和签到不能信任前端自行传入的用户身份；预约成功后起算30分钟、体育开始后15分钟等规则保持不变。
- 扫码首先识别对应资源或签到入口；是否允许签到/签退由服务端结合当前用户、预约和时间校验。扫码成功不直接等于业务签到成功。
- 接口变更先更新契约，再同步相关开发人员；在对应PingCode工作项记录影响，避免前后端各自静默更名。

## 四、开发启动要求

1. 初始化前后端工程，固定依赖与构建版本。
2. 准备数据库初始化或迁移脚本、配置示例与启动说明。
3. 配置格式检查、TypeScript类型检查、构建和相关测试。
4. 跑通一个页面与一条后端接口的联调，再按Sprint计划并行开发。
5. 团队共同制定DoD，明确代码检查、测试、联调、演示与文档更新要求。

## 五、待确定的选项

- 接口文档：仓库内OpenAPI文档，或Apifox。
- 扫码入口：手机相机扫描后打开网页，或系统网页内调用摄像头扫描。
- GitHub协作者名单及具体评审人员。
- Spring Boot具体版本、Maven构建配置与格式检查工具，由开发人员在初始化时统一。
